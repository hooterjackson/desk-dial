# Nano_D++ LCD host renderer

This harness builds the device's actual LVGL9.0.0 software renderer with the
Microsoft Visual Studio2022 Build Tools already installed on this PC. It runs
without a window, USB access, device actions, network access, or Python packages.

Run from the workspace:

```powershell
& 'app/.venv/Scripts/python.exe' './harness/build.py'
```

An optional argument sets the output directory. The default is `rendered/` next
to this file. It creates240x240 RGB565-rendered PPM files and lossless PNG copies.
Do not infer physical LED brightness, LCD viewing angle, or haptics from these.

If `firmware/src/cc_display.cpp` exists, the build compiles it directly
with `cc_display.h`, `cc_presentation.h` and `cc_icons.cpp`. Required API
(cc5.3; see "cc5.3 artwork2 on the LCD" below):

```cpp
// artwork2 lookups (store adopt/release, JPEG decode); any member may be nullptr.
void cc_display_set_media(const CCDisplayMedia& media);
// Two caller-owned 240x240 RGB565 buffers (CC_ART240_BYTES = 115,200 B each),
// front and back; PSRAM on the knob, static arrays here. The back buffer may be
// nullptr (covers written in place), both nullptr means no artwork.
lv_obj_t* cc_display_create(uint8_t* art240Front, uint8_t* art240Back);
// artwork120: the v1 120x120 RGB565 LE cover for frame.artKey
// (CC_ART120_BYTES = 28,800 B), or nullptr; artwork2 covers come from the store.
void cc_display_render(const CCFrame& frame, const uint8_t* artwork120);
```

`CCFrame` and `CCButton` are expected to retain their existing platform-neutral
char-array/scalar fields. Without this component, the harness renders a simple
LVGL baseline so the toolchain can be validated independently.

Rendering is performed by LVGL, not by a browser, Pillow, Tk, or an approximate
font engine. Montserrat56 is not included in this LVGL release; the largest
shipped size is48.

## Firmware-faithful configuration (cc5 Stage 1)

- `lv_conf.h` is generated by `build.py` from the firmware's
  `firmware/include/lv_conf.h`, byte for byte, with a header comment
  and exactly one host override:

  | Macro | Firmware | Host | Why |
  |---|---|---|---|
  | `LV_USE_TFT_ESPI` | 1 | 0 | ESP-only SPI display driver; the host flushes into a framebuffer. |

- Re-run `build.py` after every change to the firmware's `lv_conf.h`. Until then the renders are evidence for the
  old config only. `build_nanod_cc5.py` rejects a firmware build whose harness copy differs from the firmware's
  (`tooling.harness_conf_problems`). This check was added on 2026-09-30: cc5.7 changed `LV_OBJ_STYLE_CACHE` to 1
  after the last harness build, so the harness had passed with 0.

  Everything else is the knob's: `LV_MEM_SIZE` 80 KB, the Montserrat set
  (12/14/16/22/32/48), draw, widget and theme settings, and the assert handler
  (`abort()`, so a failed assert ends the renderer at once; `build.py` still runs
  it under a 900 s timeout so any hang fails the build). Do not edit `lv_conf.h` here; edit the firmware file.
- The display uses `LV_DISPLAY_RENDER_MODE_PARTIAL` with an 11,520-byte draw
  buffer, exactly like `lv_tft_espi_create()` in `lcd_thread.cpp`. The flush
  callback copies each strip into a static 240x240 RGB565 framebuffer outside
  the LVGL heap, which `save()` writes as PPM (then PNG).
- `lvgl-heap.json` in each output directory records `lv_mem_monitor()` after
  all renders.
- `cpp11_gate.py` runs first and fails the build if any shared firmware unit
  (`cc_lights.cpp`, `cc_display.cpp`, `cc_icons.cpp`; extend `SHARED_UNITS`) is
  not valid in the device's `-std=gnu++11` (real ESP32-S3 GCC 8.4), names a
  C++14/17 feature, or odr-uses a class `static constexpr` member. MSVC cannot
  check this (its minimum is C++14). `light_tests.py` runs the same gate.
  Since 1.0.0-cc5.2 it covers `cc_led_wire.cpp` too and also checks firmware
  source rules over `src/`: no `FastLED.addLeds<...>` (a FastLED clockless
  controller would bring back FastLED's own ESP32 RMT driver, whose unbounded
  wait hung the HMI task in 1.0.0-cc5.1), no other RMT user, no FastLED ESP32
  driver option (comments are ignored).
- `led_wire_tests.py` (1.0.0-cc5.2) runs the gate, then builds
  `led_wire_tests.cpp` with the unchanged firmware unit `cc_led_wire.cpp` (MSVC
  `/W4 /WX`): the RMT item words must equal FastLED 3.6.0's WS2811 `mOne` and
  `mZero` recomputed from FastLED's own formulas (25/25 and 12/38 ticks at
  40 MHz), MSB first, whole bytes only; 200 pseudo-random frames are then
  checked against an independent Python encoder.
- CMake: shared firmware units are an OBJECT library in C++14 (MSVC minimum);
  only the driver `main.cpp` uses C++17 (`std::filesystem`). The ArduinoJson
  include path is available for later parser units; generated fonts
  `src/fonts/cc_font_*.c` are picked up automatically once they exist.
- Artwork fixtures: `app/assets/fixtures/art-hall-120.rgb565`
  and `art-bright-120.rgb565` (see the README there; create them with
  `make_art_fixtures.py`). The fixture directory is compiled in and can be
  overridden with a second argument: `build.py <out> <fixture-dir>`.
  `art-hall-volume` and `art-bright-recent` exercise the two-argument API with
  real covers; the Stage 1 renderer ignores artwork, so they match `volume` and
  `recent` until the Stage 6 renderer draws it.

Stage 1 evidence: `build.py harness/cc5-stage1`. The 16 `before-*`
old-renderer frames and 4 icon sheets are pixel-identical to the cc4 renders
made with the previous 4 MB/FULL-mode host configuration; the product frames
keep identical lit-pixel geometry and differ only by the later `CCInk` token
values in `cc_presentation.h`.

## Selected Quiet Listening design

`cc_display.cpp` is now the actual firmware host screen renderer and is compiled
unchanged into this harness. Run the build with `harness/quiet-listening`
as its output argument, followed by `quiet_sheet.py`. It produces16 native
240x240 states plus `quiet-four-controls.png` and `quiet-all-states.png`. Every
sample includes the four physical button legends. Samples cover two-line long
titles,100% volume, pending readback, loading, unavailable content, More, all
three transport positions, focus failure, network loss, and a closed window.

`geometry-checks.json` counts any nonblack pixel outside the120px LCD radius.
`typography-checks.json` uses actual LVGL font metrics: all twelve footer
legends fit the47px columns (Browse is widest at45px). These checks establish
raster geometry, not real viewing-angle or brightness acceptance.

The shipped Montserrat font subset lacks accented Latin, typographic
punctuation, CJK, and emoji. Two samples demonstrate the companion's device-only
ASCII normalization (`Renee Lys - Mare Alta` and `It's All Right - Live`). Full
original text remains a companion/provider concern. The native counter uses an
ASCII vertical separator because the font lacks a middle-dot glyph.

`reference_comparison.ps1` makes a side-by-side design comparison. Its left pane
uses the user-selected conceptual image's approximate inner LCD crop
(x300,y171,width655,height655), proportionally normalized to240px and masked to
a circular aperture. Its right pane uses the unscaled native LVGL volume
render. Neither image claims to be a photograph of the running device. Source
typefaces are approximate in the generated concept; the implementation uses
the device's real Montserrat fonts at12,14,22,and32px. The divider is displayed
only when a volume title fits one line, preserving two-line metadata space.

## cc3 viewing-angle correction

The `quiet-listening/` evidence above is preserved as the installed cc2 baseline.
The current firmware renderer uses 14 px footer type at y160, 24 px above its
previous y184 position. The four columns have x positions 24, 74, 134, and 167

## cc5.3 artwork2 on the LCD (ARTWORK2.md section 7)

The renderer now takes two 240 px buffers, `cc_display_create(front, back)`
(two PSRAM buffers on the knob, allocated in `lcd_thread.cpp`; two static arrays
here), and its artwork2 lookups through `cc_display_set_media(CCDisplayMedia)`:
`adopt`/`release` (the knob's `cc_media_adopt`/`cc_media_release_display`) and
`decodeCover` (`cc_jpeg_decode_240`). `cc_display.cpp` stays platform-neutral.

- Covers: when the key to draw changes, the artwork2 store is asked first (JPEG
  decoded into the back buffer), then the v1 store (120 px upscaled into the
  back buffer); the buffers swap and the image is re-pointed. Going back to the
  cover still held by the back buffer is a swap without a decode. A decode
  failure shows no art for that key until the frame's `artKey` changes. Fades,
  `artDim`, idle and late arrival are unchanged; identical frames re-decode
  nothing. The store's display pin is held while a cover is drawn and released
  when none is, and on native handback (`cc_display_release_media()`).
- Intended behaviour beyond section 7's "else: no art": a key whose pixels a
  display buffer still holds (the front buffer, or the back buffer after a
  swap) is drawn even when neither store has the key any more, for example on a
  return after handback and eviction. Keys are content hashes, so those pixels
  are exact; the artwork2 store's displayed slot is then -1 (no pin). FakeKnob
  and host-device authors must not assume "store miss = no art" on the LCD.
  Icons are stricter: the tile shows an icon only on a store hit, otherwise the
  letter tile.
- The cover lookup and decode run first in `cc_display_render()`, before the
  render starts any animation. LVGL times an animation from `lv_anim_start()`,
  so a decode (up to about 150 ms on the knob) after the screen-change tweens
  would cut that much off the slide and fade.
- With one art buffer (`cc_display_create(front, nullptr)`, the knob when the
  second PSRAM allocation fails) new covers are decoded in place: no back-buffer
  reuse, and a failed decode leaves the shown buffer overwritten, so the art
  hides and the next key is decoded again.
- Windows tile: the selected window's 32x32 RGB565 icon (`iconKey`) fills the
  tile when the store has it (copied into a static 2 KB buffer when the key
  changes; transparent tile, letter hidden, no fade); otherwise the `#444` letter
  tile, whose ASCII a-z initial is upper-cased. The closed entry keeps the tile
  group at opa 89 either way.

Fixtures: `make_art_fixtures.py --artwork2` writes `artwork2/` (deterministic):
`cover-hall-240.jpg` (the real Hall composite), `cover-bright-240.jpg` and
`cover-detail-240.jpg` (synthetic, through `prepare_artwork()`), all encoded like
the host (section 5 quality ladder, 4:2:0, baseline); `cover-progressive-240.jpg`
(forces a decode failure); three 2048-byte icon payloads (section 5 composite
onto black and RGB565 rounding) with PNG previews; `manifest.json`. The harness
frames use the manifest names as keys.

JPEG glue: CMake compiles the firmware's `src/cc_jpeg.cpp` with every source in
`tjpgd_shim/` (fw-core), whose headers shadow the ESP ones. Without them it
builds `jpeg_standin.cpp` (the same TJpgDec) and records `jpeg_glue: "standin"`,
which fails the report. Note: LVGL's copy of TJpgDec writes pixels as B, G, R;
the ESP ROM decoder writes R, G, B, so a host shim must swap them.

Harness additions (`main.cpp`): a store stand-in (committed payloads per case or
timeline step, the displayed key per kind), 15 `artwork2` cases (JPEG covers on
nowPlaying/recent/tracks with and without `artDim`, the detail cover, a decode
failure, a cover not committed yet, icons open/closed/without subtitle, letter
tiles in lower case, with a missing icon and with a non-ASCII initial) and six
timelines (`a2-heartbeat` with commits of unrelated keys, `a2-icon-late`,
`a2-cover-late`, `a2-swap`, `a2-decode-fail`, `a2-slide-decode`), plus a
`handback` sequence in `render-index.json` (release, return, return after
eviction). `a2-slide-decode` simulates the knob's decode time: the fake tick
moves 150 ms inside the decode (`Step::decodeMs`, no LVGL timer meanwhile) and
that step's captures are timed from the end of its render.

`build.py` runs the harness twice: the full run, then `lcd-preview.exe
--one-buffer <out>/one-buffer` (a single art buffer; artwork2 cases, timelines
and handback only). It configures CMake with `-DNANOD_FIRMWARE_SRC` and
`-DNANOD_TJPGD_SHIM` pinned to the real directories, so an override left in the
`build/` cache cannot produce evidence from an overlay; `render-index.json`
records both paths (`firmware_src`, `tjpgd_shim`) and each cover fixture's
decoder output (`decoded/<name>.rgb565`, native RGB565, through the same glue).

`cc5_report.py` adds `jpeg_glue` (glue and source paths), `a2_cover_exact`,
`a2_cover_fullres`, `a2_cover_none`, `a2_icon`, `a2_letter`, `a2_media_pins`,
`a2_heartbeat`, `a2_timelines`, `a2_handback` and `a2_one_buffer` (see its
docstring); every earlier check is unchanged. On evidence from before this
harness (for example a `cc5-handoff` built by cc5.2) the artwork2 checks fail
with "evidence predates the cc5.3 harness: rebuild with build.py" instead of
stopping the report. Regenerate the handoff with the two commands above.

Exact covers: `a2_cover_exact` needs no tolerance. Every art-only pixel of the
cover renders (the seven cover cases, a swap back to the back buffer, the cover
after a failed decode, the cover decoded during a screen change) must equal
`cc_jpeg_decode_240`'s output for that key. For `artDim` the output is mixed
over black at image_opa 112 the way LVGL does it (`c * ((opa + 4) >> 3) >> 5`).
The one-buffer run is held to the same rule.

Cover tolerance (the secondary check): against a Pillow (libjpeg) decode rounded to RGB565, the art
pixels must reach luma PSNR >= 40 dB (the contract's figure, applied where a
4:2:0 cover's resolution lives) and beat a 120 px round trip; RGB needs >= 30 dB.
TJpgDec replicates chroma instead of libjpeg's "fancy" upsampling, and a 5-bit
channel turns +-1 decoder differences into 8-unit steps, so RGB PSNR is 33-44 dB
on these fixtures while luma is 45-49 dB. The detail cover's 120 px round trip
stays near 23 dB, so it proves full resolution.

## r4 motion, LEDs and render speed (plan stage F4; MOTION.md in the firmware tree)

- `make_motion.py [--check]`: the four r4 springs baked into `cc_display.cpp` `kSpringLut` (the r3.1 prototype's
  `cssSpring()`); `--check` fails when the table is stale.
- `export_morph_strip.cjs [--check]`: the M9 Play <-> Pause morph, 12 A8 frames of the 20 px glyph
  (`src/cc_icon_morph.cpp/.h`), drawn with the icon exporter's renderer and stroke.
- `make_crumbs.py` now lays the crumb out by `crumb_arc.display()` (README 3.6: at most two named levels, 190 px of
  arc, else `‹ CURRENT`).
- Harness timelines `r4-moments`, `r4-reduced` (M1-M15, the input moments through `cc_display_input()` /
  `cc_display_wall()` like lcd_thread) and `r4-tour` (README 8 on the r3 screens); `cc54_report.py` `r4_moments`.
  `r4_tour_sheet.py <render-dir> [out.png]` draws the review sheet (default
  `app/design-reference/r4-motion-tour-sheet.png`), with the LED moments from the twin.
- `perf.py <label> [--rows 24,48] [--cycles N] [--period 12] [--repeat 5] [--out DIR] [--conf DIR]` builds `lcd-perf` (`perf.cpp`) and profiles M1 / M4 /
  M13 refreshes at the knob's LVGL period (`--period`, default 12 ms = binary F; 16 = binary D and the older files) (host µs, pixels, chunks, layered objects, A8 copies, per-task time, a content-redraw breakdown)
  into `perf/<label>.json`. `--conf DIR` compiles LVGL with `DIR/lv_conf.h` in `build-perf-conf/` (a candidate
  lv_conf.h change measured before it is proposed; CMake `NANOD_LV_CONF_DIR`, never set by `build.py`).
  `CMakeLists.txt` pins Release `/O2 /Ob2 /DNDEBUG` on `lvgl`, `firmware_shared` and `lcd-perf` (and a non-incremental
  link): `build/`'s old cache had empty Release flags, so its runs were `/Od` while `build-perf-conf/` was `/O2`.
  Every run records `release_flags` and `lv_conf_sha256`; perf.py refuses a build without `/O2`, and
  `perf.py --compare A.json B.json` refuses files built at different or unrecorded levels. Files made before
  this (`before`, `after-r4`, `baseline-cc5.7`: `/Od`; `stylecache`, `after-r4-stylecache`: `/O2`) are not
  comparable with each other; `baseline-cc5.7-o2` is the re-taken cc5.7 baseline (12 ms, `/O2`).
  `--repeat N` (default 5) runs N interleaved rounds of every rows variant (one run's median moves 15-40 % on a PC,
  more than the effects being ranked) and records per scenario `us_medians`, `us_median_min` and
  `us_median_of_runs`; `--compare` uses the median over runs. `--out DIR` writes outside the tracked `perf/` (audits).
